# 外置读取原理

这份文档解释 `worldbox_agent` 到底是怎么把游戏里的世界变成磁盘上的 JSON 的。
不需要懂 C# 或逆向，只需要一点文件与数据格式的常识。

---

## 一、为什么外置读取是可行的

一般的"游戏外置工具"有两条路，都很痛苦：

1. **读游戏内存**——需要找到基址、逆向对象布局、跟随指针链。
   游戏一更新，偏移全变，工具就废了。风险高、维护难。
2. **Hook / 注入进程**——本质上是写一个 mod，还可能被反作弊或稳定性问题困扰。

WorldBox 提供了一条**第三条路**：它自己会定期把整个世界**序列化成文件写到磁盘**。
我们要做的就是**读那些文件**。这件事的美妙之处在于：

- **不碰游戏进程**，所以不会让游戏崩溃、不会被当成作弊、不需要管理员权限
- **格式是游戏自己定义的稳定协议**（存档格式还要保证老存档能读），
  比内存布局稳定得多
- **实现只需要标准库**——读文件、解 JSON、查 SQLite，不需要任何第三方依赖

代价是**延迟**：我们只能看到游戏最近一次存档的状态，而不是每一帧。
对"国家领袖做宏观决策"这个用途来说，这个代价完全可以接受。

---

## 二、三个数据源

WorldBox（Windows / Unity / Mono）把数据放在：

```
%USERPROFILE%\AppData\LocalLow\mkarpenko\WorldBox\
├── autosaves\<unix时间戳>\      ← 自动存档，约每 5 分钟一个
│   ├── map.wbax                 完整世界状态（纯 JSON）
│   ├── map.meta                 小型元数据
│   ├── map_stats.s3db           SQLite：逐年统计 + 事件流水
│   └── preview.png              缩略图
└── saves\save1\                  ← 手动保存
    └── map.wbox                 同样的世界状态（zlib 压缩）
```

`mkarpenko` 是开发者的 Unity 公司名，`WorldBox` 是产品名——这是 Unity 在
Windows 上放 `Application.persistentDataPath` 的默认位置。

### 2.1 `map.wbax` / `map.wbox`：世界快照

**这是最关键的发现在于：`map.wbax` 就是纯文本 JSON。** 文件开头是
`{"saveVersion":17,...}`，用任何文本编辑器都能打开（我们这份 24 MB）。
顶层结构大致是：

```
saveVersion, width, height, mapStats,
tileMap, tileArray, fire, frozen_tiles,
kingdoms[], cities[], actors_data[], buildings[],
armies[], wars[], alliances[], relations[],
cultures[], languages[], religions[], subspecies[],
clans[], families[], plots[], books[], items[]
```

每个 `kingdoms[i]` 是一条国家记录，字段如 `id, name, kingID, capitalID,
color_id, renown, saved_traits, past_rulers, total_kills, ...`。

`map.wbox` 是**同一份 JSON 做 zlib 压缩**。判别方法很简单：

```python
raw = path.read_bytes()
if raw[:1] == b"{":          # 纯 JSON
    data = json.loads(raw.decode("utf-8-sig"))
else:                        # zlib 流（0x78 开头）
    data = json.loads(zlib.decompress(raw).decode("utf-8-sig"))
```

为了稳妥，解压时依次尝试 `wbits = 15 / -15 / 47`，覆盖 zlib、raw deflate
和 gzip 三种包装。

### 2.2 `map_stats.s3db`：历史与事件

**这是本工具最有价值的数据源**，因为 JSON 快照只有"当前一帧"，
而这里存着**记忆**。它就是一个标准 SQLite 文件（文件头 `SQLite format 3.`），
里面 110 张表，其中与领袖决策最相关的：

| 表 | 内容 |
|---|---|
| `KingdomYearly1 / 10 / 100` | 每个国家**逐年/十年/百年**的 48 个指标：人口、成年、儿童、军队、国库、粮食、领土、建筑、饥饿、无家可归、声望、死因…… |
| `CityYearly*` | 每座城市的同类序列 |
| `WarYearly*` | 每场战争的逐年数据 |
| `WorldYearly*` | 世界层面的逐年汇总（总人口、城市数、战争数、生物量……） |
| `WorldLogMessage` | **事件流水**：国王更替、城市被毁、叛乱、战争爆发，带年份与坐标 |

有了 `KingdomYearly1`，agent 才能看出"这个国家人口从 2921 掉到 1556 又回到
1716"这样的故事——**只看当前快照是绝对读不出趋势的**。这是本工具与
"截个图给 AI 看"最本质的区别。

### 2.3 ⚠️ 只读也会锁住游戏：`map_stats.s3db` 必须读副本

**这一条是本项目遇到过最严重的坑：工具一开着，游戏就存不了档。**

症状（游戏自己的 `Player.log`）：

```
Error during saving
System.IO.IOException: The process cannot access the file
'C:\...\WorldBox\saves\save3\map_stats.s3db' because it is being used by another process.
  at db.DBManager.saveToPath (System.String pPath) ...      ← 注意：失败在 File.Delete
  at SaveManager.saveStatsIn → saveMapData → saveToCurrentPath → clickSaveSlot
```

**机制**：WorldBox 存档时**先删除再重写**存档目录里的 `map_stats.s3db`
（`DBManager.saveToPath` 第一步是 `File.Delete`）。而 **SQLite 在 Windows 上打开
文件时不共享「删除」权限**，所以只要工具还开着那个文件，游戏这次存档就一定失败。
实测判据（申请 DELETE 权限、不真删，`Win32 错误 32 = ERROR_SHARING_VIOLATION`）：

```
工具式连接（mode=ro&immutable=1）打开之前 → ✅ 可删除
同一连接保持期间                        → ❌ 被阻止(err 32)
```

**最容易踩到的情形**：把工具指向**你正在玩的那份手动存档**（`saves\saveN`）——
这恰恰是最自然的用法（"我要看我现在这个世界"），于是游戏再也存不了那个世界。
自动存档会不断新建目录，所以症状不那么明显；手动存档（同一个 `saveN` 反复覆盖）
则必然中招。

**解法：读副本，别读原件。** `StatsDatabase.open()` 先把 `.s3db` 整个复制到临时
文件，再用只读方式打开副本（`_copy_db_to_temp()`）。这样工具手上没有任何游戏文件
的句柄，游戏随时都能存；顺带还避免了"读到写了一半的库"——`immutable=1` 原本想解决的
正是这个问题，但它的代价太大。复制失败时重试若干次（游戏可能正在写），临时目录
不可用时才退回直接打开，并在 `note` 里如实说明代价。

回归测试在 `tools/test_pipeline.py` 第 7 节：库开着时，**游戏那份必须仍可被
`os.replace` 掉**（等价于"游戏能存档"）。

> 顺带一条同样的教训：`worldbox_selection.json` 会在**游戏数据目录**和**工具自己的
> 输出目录**两处出现（前者不可写时退到后者）。两个文件都存在时，必须**以
> `updated_at` 最新的那份为准**，否则一份旧选择会盖住新选择——症状是"我明明选了
> 它，服务却在读另一个世界"，而这个 bug 正好会把工具指到错误（甚至是你正在玩的）
> 存档上。

## 三、从文件到情报的处理链

```
map.wbax / map.wbox ──┐
                      ├─→ decode_payload()  → 原始 dict
map_stats.s3db ───────┘                      │
                                             ▼
                              load_world()  构建 WorldSnapshot
                                             │  · 按 id 建索引
                                             │  · 算派生量（人口/军队/领土/建筑）
                                             │  · 查询历史与事件
                                             ▼
                              views.py      转成中文视图
                                             │  · kingdom_self_view   本国国情
                                             │  · others_view         列国简报
                                             │  · world_overview      世界概览
                                             ▼
                        export.py / server.py
                        · 分国家写盘（每国一个文件夹）
                        · 或经本地 HTTP 接口对外提供
```

### 3.1 派生量是怎么算的

快照里的原始字段不够用——比如**国家的人口**没有任何一个字段直接给出。
所以要从单位记录里聚合，而**口径必须逐个核对**，因为想当然很容易错：

| 指标 | 正确算法 | 踩过的坑 |
|---|---|---|
| 人口 | `actors_data` 里 `civ_kingdom_id == 该国` 的条目数，**排除船只** | 不排除船只时，同一个国家在不同文档里会出现两个人口数 |
| 军队 | 上述条目中**带 `army` 字段**（值为军队 id）的数量 | 一开始去读 `cities[].army`——**城市记录里根本没有这个字段**，所以恒为 0 |
| 领土 | 该国各城市 `zones` 数组长度之和 | `zones` 是一格一条，长度就是面积 |
| 建筑 | `buildings` 里 `cityID` 属于该国城市的条目数 | 城市记录也没有 `buildings` 字段 |
| 城市坐标 | 该城 `zones` 所有格子的**重心** | 城市记录不存坐标，只能自己算 |

口径对了之后，结果可以和游戏自己的统计互相印证：
本工具算出大仁军队 309，`KingdomYearly1` 最新一行是 356——
差异来自"逐年统计是年初记一次、而即时值反映存档时刻"，两者都对。

**这个交叉验证很重要**：它是我们确认自己没读错字段的唯一手段。

### 3.2 三个工程细节（都是踩过坑才写对的）

**一、只读打开 SQLite，避免抢锁。**
游戏可能正持有这个文件，所以用 URI 参数以只读 + 不可变模式打开：

```python
sqlite3.connect(f"file:{path}?mode=ro&immutable=1", uri=True)
```

`immutable=1` 告诉 SQLite"这个文件不会变"，从而跳过加锁。

**二、跨线程使用连接。**
HTTP 服务在主线程构建快照，却在工作线程里响应用户查询。
sqlite3 默认禁止跨线程复用连接，会抛
`SQLite objects created in a thread can only be used in that same thread`。
解法是 `check_same_thread=False` 加一把锁串行化访问。

> 这个 bug 的表现极具迷惑性：启动时读事件日志（主线程）一切正常，
> 请求历史数据（工作线程）却**静默返回空列表**——因为异常被
> `except sqlite3.Error` 吞掉了。所以现在查询失败会记进 `db.error` 而不是无声咽下。

**三、`PRAGMA table_info` 的陷阱。**
为了按列名取字段，连接设了 `row_factory = sqlite3.Row`。
但 `PRAGMA table_info` 返回的行是 `(cid, name, type, ...)`，
在 `Row` 工厂下 **`row[0]` 是列序号（0,1,2…）而不是列名**。
于是"匹配字段名"这一步永远匹配不上，生成的 SQL 变成 `SELECT  FROM ...`，
查询返回空——**同样不报错**。

```python
# 错的：row[0] 拿到的是整数列序号
cols = [r[0] for r in self._query('PRAGMA table_info("KingdomYearly1")')]
# 对的：索引 1 才是列名
cols = [r[1] for r in self._query('PRAGMA table_info("KingdomYearly1")')]
```

这两个静默失败是同一个教训：**"没有数据"和"报错"必须区分开**。
现在每个文档里都带数据源状态，工具自身也有回归测试专门覆盖这条路径。

### 3.3 原子写入

agent 可能在我们写文件的同一瞬间去读。所以不能直接往目标文件写：

```python
fd, tmp = tempfile.mkstemp(dir=path.parent, prefix=".tmp-")
with os.fdopen(fd, "w", encoding="utf-8") as fh:
    fh.write(data)
os.replace(tmp, path)     # 同一文件系统内的原子替换
```

`os.replace` 在 Windows 上也是原子的，所以读者要么看到旧文件、
要么看到完整的新文件，**永远不会看到半个 JSON**。

## 四、"实时"到什么程度

必须诚实说明这个方案的边界：

| 环节 | 延迟 |
|---|---|
| 游戏自动存档间隔 | **约 300 秒**（实测 5 个连续自动存档间隔为 300/360/300/300 秒） |
| 我们的轮询间隔 | 默认 10 秒（`--interval` 可调） |
| 合计 | 通常 0–5 分钟 |

**这是游戏本身的节奏，外置工具无法改变它。** 想立刻刷新，
在游戏里手动按一次保存即可——下一次轮询（10 秒内）就会读到。

因此每份文档都带 `world.存档距今秒数`，超过 600 秒还会附加 `_警告` 字段，
`wb.py` 同时在 stderr 上提示。**agent 应当检查这个数字**，
不要把 3 小时前的战报当实时局势——skills 里对此有硬性要求。

---

## 五、这个方案的取舍

**优势**

- 零依赖（仅 Python 标准库）、零注入、不干扰游戏
- 对游戏小版本更新不敏感：只要存档格式不变（`saveVersion` 字段可检测），工具就不用改
- 附带 `map_stats.s3db` 这个**历史数据宝库**，是"截图给 AI 看"做不到的
- 崩溃安全：读文件失败最坏情况是"这次没刷新"，不会影响游戏

**劣势**

- 有 0–5 分钟延迟，做不了逐帧反应
- 依赖游戏愿意写盘；如果某版本改成只写加密/二进制格式，就要重做解析
- `width`/`height` 这类字段语义可疑（实测是内部分块数 4×4，而非地图尺寸），
  所以地图边界改成从实际坐标**实测**得出，不信任该字段

**如果将来需要"真·实时"**，唯一干净的升级路径是在游戏内跑一个小桥接
（通过已安装的 BepInEx 挂一个插件，每帧把状态写到同一个目录）。
那样读取端完全不用改——因为**接口就是磁盘上的那份 JSON 格式**。
这已经越过了"非 mod"的边界，需要你明确同意才做。
