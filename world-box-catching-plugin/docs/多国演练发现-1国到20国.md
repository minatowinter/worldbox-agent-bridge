## 3. 发现的问题

### 3.0 先记一条环境残留（已修）

`data\worldbox_selection.json` 里是 `"绝对不存在的存档"`——不是代码 bug，是上一次手工实验（多半在测回退路径）留下的。
`paths.resolve_save()` 匹配不上会**带警告地回退到最新**（`server.py:119`），导出看不出异常，但选择状态实际是坏的，`saves` 会显示「当前选择: 绝对不存在的存档」。
**已清理**（`select latest` → `selected_save: null`），随后才锁到 #7。

### 🔴 P1 战争「敌方」恒空，共同交战国被判成敌人

**现象**：`composePrompt()` 生成的自动人设里有一句病句（实测原文）：

```
你目前正在打 3 场战争：对；对；对。
```

**证据**：

1. **全部 24 条战争记录（20 国）`敌方` 都是空数组**，非空 0 条。
2. `others.正在进行的战争` 抽样 4 场，**`防守方` 全为空**：
   - 明关冲突：进攻方 `['中华帝国','塔罗共和国']`，防守方 `[]`
   - 东北社会主义阵线圣战：进攻方 `[]`，防守方 `[]`（双方都不存在了，却仍列在「正在进行」）
3. 但 `self.diplomacy.对外关系`（19 条）与 `敌人`（2 条）**是有内容的**，且内容是：
   `Lyhora 关系=交战`、`塔罗共和国 关系=交战`。
4. 而原始战争记录显示这两个国家**和中华帝国同阵营**：
   - 明关冲突（id 23）：我方角色=进攻方，`共同交战国: [塔罗共和国]`，`敌方: []`
   - War of Lyhora（id 10）：我方角色=进攻方，`共同交战国: [Lyhora]`
   → **「敌人」列表恰好等于「共同交战国」列表。**

**根因**（代码与注释不一致）：

- `views.py:404-407` 的注释写「战争关系按『双方是否出现在同一场战争的两侧』判断」，
  但代码只判断**是否出现在同一场战争里**，没有判断「两侧」：
  ```python
  at_war = bool(set(snap.kingdom_wars.get(kingdom_id, []))
                & set(snap.kingdom_wars.get(oid, [])))
  ```
- `build.py:394-400` 的 `enemy_ids_of()` 把 `list_attackers + list_defenders` **合并**当敌人，
  在「防守方恒空」的数据下，只能捞到同阵营的共同交战国。
- `views.py:378-382` 的 `敌方` 由 `opponents`（真正的对侧）生成 → 恒空。
- 桥的 `worldbox-bridge.js:284-288` 用 `敌方` 填 `我的战争` → 恒空 → `composePrompt`（`:550-553`）拼出「对；对；对」。

**影响**：agent 会被告知「塔罗共和国与你是敌对」，而它其实是同一场战争的**共同交战国**。
在一场真实演练里，这足以让某个领袖提议攻打自己的盟友。这是本次演练里**对决策危害最大的问题**。

**建议**：

1. `关系码` 改为「同场战争中是否位于对侧」；对侧为空时如实标注「对手已灭亡/未记录」，而不是判成敌人。
   —— 项目里已有现成写法可循：`views.py:686` 会输出「已灭亡」，`views.py:419` 已有 `是否已灭亡` 字段。
2. `composePrompt` 在 `敌方` 为空时**不要输出「对」**，改成「有 N 场战争的对手未见记录」。
3. 「正在进行的战争」应过滤掉**双方全部灭亡**的记录（如 id 24），或明确标为「已结束/无存活方」。

### 🔴 P2 注入的 8 个邻国按声望选，不按距离

**现象**：中华帝国的 system prompt 里带着 **33.1 格**外的 Greeshi 的每一座城坐标，
却看不到 **5.8 格**外的塔罗共和国——而同一段注入规则的第 5 条正是「**先查距离再决定调兵**」。

**证据**（实测：14 座城 vs 19 个对手，最近距离）：

```
★ Red Pe Zez    4.1 格  声望 2317   ← 被注入
✗ 塔罗共和国      5.8 格  声望 1582   ← 被砍掉（最近的第 2 名）
✗ Lyhora        6.1 格  声望 1658   ← 被砍掉（最近的第 3 名）
★ 利剑联合王国     6.7 格  声望 2464
★ Greeshi      33.1 格  声望 1741   ← 被注入（注入名单里最远）
```

真正最近的 3 国里**只有 1 个被注入**；被砍掉的 11 国中最近的是塔罗共和国（5.8 格）。

**根因**：`others_view` 遍历 `snap.live_kingdoms()`（`views.py:699`），而 `live_kingdoms()`
按 `(renown, population)` 降序（`build.py:347-350`）；桥再 `slice(0, 8)`（`worldbox-bridge.js:289`）。
于是「前 8 名」= **声望最高的 8 个**，与地理威胁无关。

**影响**：多国世界里 agent 的军事决策依据（邻国、距离、可攻击目标）系统性缺失，
正是 `game-data-agent-bridge` skill 里「把离敌人 26 格的部队派去打」那类错误的成因。

**建议**：`列国` 改取「**距离最近的 N 个** ∪ 声望最高的 M 个」并集；
并在 `_note` 里写明「这里不是全部邻国，查距离请用 `world_state` 工具」。

### 🟠 P3 注入体量超出承诺

**实测**：`systemSection()` = **13.8 KB**；同段代码注释承诺「约 3–5 KB」（`worldbox-bridge.js:347`），`process.md` 记的是 5.4 KB。

**分解**（`contextFor()` 共 7.6 KB）：

| 分支 | 体量 |
|---|---|
| **列国** | **4.8 KB** |
| 我的国家 | 1.2 KB（城市已按设计限 8 座，共 14 座） |
| 趋势 | 0.6 KB |
| 我的战争 / 近期大事 / 数据新鲜度 / 角色 | 0.9 KB |
| 关系矩阵 | 0.0 KB（空，见 P6） |

`列国` 的 4.8 KB 里有 **2.8 KB 是对手城市明细（46 条城市）**：
`worldbox-bridge.js:294-296` 对每个对手的 `城市列表` **不做上限**，
而「我的国家」是限 8 座的（`:273-277`）——**对自己的国家做了压缩，对 8 个对手却没做**。

**影响**：20 角色一轮固定注入约 **13.8 KB × 20 ≈ 276 KB**，且随着地图变大线性增长。

**建议**：对手城市也加上限（例如只给最近/最大的 N 座 + `_说明`），或把 `列国` 的城市明细
整体移到 `world_state` 工具按需取。

### 🟠 P4 `/health` 谎报「跟随最新存档」

**实测**：状态文件锁在 `1786604527`，`/health` 同时返回
`using: "1786604527"` 与 `mode: "跟随最新存档"`、`requested: null`。

**根因**：`server.py:145-150` 的 `mode` 由 `self._requested_selector` 决定，
而它只在 `select_save()`（进程内切换）里被赋值，**启动时永远是 `None`**；
持久化选择只进了 `_used_key`。所以「启动时读到一把锁」会被描述成「跟随最新」。

**影响**：这正是前端（`process.md` 5.1）要渲染的字段，会把「已锁定 #7」显示成「跟随最新」；
`process.md` 1.2 记的「当前选中的存档是 Skulls of Misery」很可能就是这么来的。

**建议**：`mode` 依据 `used` 与持久化状态判断，或补一个 `selectedVia: "state-file" | "cli" | "latest"`。

### 🟠 P5 `list` / `show` / `doctor` 无视持久化选择

**实测**（锁定 #7 之后）：

```
export  → 20 国，来源 1786604527      ✅ 遵守选择
list    → 世界: Skulls of Misery，只有「大仁」  ❌ 无视选择
show 中华帝国 → 没有找到匹配，退出码 2         ❌ 无视选择
```

**根因**：`worldbox_agent.py:384/403/408` 给这三个命令用了 `common(p, out=False)`，
而 **`--out` 同时是「状态文件回退位置」的载体**（`_pick_save(args, out)` → `state_fallback=out`）。
它们不接受 `--out`，于是 `load_selection(root, None)` 只在**游戏数据目录**里找状态文件；
本机游戏目录不可写、状态文件落在 `data\`，因此读不到。
（`doctor` 另有 `worldbox_agent.py:125` 直接取 `latest`，措辞「本次选用」也容易误导。）

**影响**：只在「状态文件落在回退位置」时发生——而**本机就是这种状态**。
使用者按 CLI 提示查国家会得到另一个世界的答案，且 `show` 的报错还建议去跑同样失效的 `list`。

**建议**：这三个命令也传 `out`（或单独加 `--state-fallback`）；
或让 `show`/`list` 优先读 `data\` 下已导出的 JSON（那才是与房间程序一致的那份）。

### 🟡 P6 `关系矩阵` 恒空，解释字段被桥丢弃

`others.json` 里 `关系矩阵 = {}`，但同文件带有 `关系矩阵说明`（64 字，说明「键为 'A|B'，值为 war/alliance」）。
`worldbox-bridge.js:299` 只注入 `关系矩阵`，**没有注入说明** → agent 看到 `"关系矩阵": {}`，
无从判断「是没数据」还是「字段没解释」。这与 skill「缺失就说缺失」那条相悖。

建议：一并注入 `关系矩阵说明`；或按 `对外关系` 现算矩阵（`views.py:726-749` 已有建矩阵的代码，只是数据源为空）。

### 🟡 P7 人格档案空缺 + 孤儿人设

- `data/agents/` 下**只有「大仁」**——那是 1 国世界里的国家，**已不在当前世界**；
- 当前 20 国**全部没有** `persona.md`（`wb.py brief` 已主动提示要 `persona --init`）。

建议：drill 前批量 init；并考虑让工具区分「属于当前世界的人设」，避免给已灭亡国家保留目录造成误读。

### 🟡 P8 趋势窗口只有约 19 年（游戏自身保留，不是工具截断）

实测：`WorldYearly1` 19 行（`God's World` 在第 78 年时是 timestamp 60~78，**也是 19 行**）；
`KingdomYearly1` 380 行 = 20 国 × 19 年。**这是滚动窗口，不是导出截断**
（`export.py:166` 用 `limit=200`、`views.py:40` `MAX_HISTORY=40`，都没卡在 19）。

建议：在 `history_meta` / `README` 里写明「最多约 19 年」，
否则 agent 可能把「窗口短」误读成「国家只有 19 年历史」——这会直接扭曲趋势判断。

### 🟡 P9 客户端正常断开会在服务端打印整段堆栈

本次 `serve` 的日志里，每一次客户端（`test_api.py`、测量脚本）正常收尾断开 keep-alive 连接，
服务端都会打印：

```
Exception occurred during processing of request from ('127.0.0.1', 57776)
Traceback (most recent call last):
  ...
ConnectionResetError: [WinError 10054] 远程主机强迫关闭了一个现有的连接。
```

**影响**：这是**正常断连**，不是故障，但它以「异常 + 完整堆栈」的形式出现，
在 PowerShell 里还会被包装成红色 `NativeCommandError`——与 `process.md` 4.9 / 本文 §5 记录的那类
「假的失败信号」完全同源，会掩盖真正的错误。

**建议**：在 handler 里捕获 `ConnectionResetError` / `BrokenPipeError` 直接静默返回（或降为 debug 级日志）。

### 🟡 P10 `/api/state` 的 `savesCount` 报成 1

实测：`GET /api/worldbox/saves` → `count = 31`；但 `GET /api/state` 的 `worldbox.savesCount = 1`。

**根因**：`server.js` 的 `worldboxInfo(room, {withSaves:false})` 调用 `bridge.saves(1)`，
只取 1 行来"省流量"；而 Python 侧 `/api/v1/saves` 的「存档数量」是 `len(rows)`
（`server.py:414`），于是被 limit 截成了 1。

**影响**：`/api/state` 里这个字段是**假数字**。前端存档选择器用的是专用接口（拿到 31），
所以没踩到；但任何人想用 `savesCount` 显示"共 N 份存档"都会被骗。

**建议**：Python 侧把「存档数量」改成总数（不随 limit 变化），或桥在 `limit=1` 时另外读总数。

### 🟠 P11 `leaderAgent()` 的默认 systemPrompt 让"世界变了才重算人设"永远不触发

**发现于**：做前端人设区（`process.md` 5.1 第 2 项）时联调，发现 `promptManual = 20`——20 位领袖居然都有"手写"人设。

**证据链**：

1. `server.js:151-158` 的 `leaderAgent()` 在**建房间时就给每位领袖写了一段非空 `systemPrompt`**（"你是 WorldBox 世界「X」的领袖…"）。
2. `worldbox-bridge.js:500-505` 先判"使用者写过人设"：`if (explicit && !opts.force) { skip }`。
3. 于是同一个函数里 `:506-510` 的 **`stale`（世界已变 → 重算）分支永远走不到**。
4. 实测：`POST /api/worldbox/prompts {force:false}` → `filled 0 / refreshed 0 / skipped 20`，
   reason 分布 `{'已有人设，未被覆盖': 20}`。
5. 而 `syncWorldboxPrompts` 的三个调用点（`server.js:1594` 建房、`:1757` 切存档、`:1780` 接口）
   **全部传 `force: true`**——也就是说"只补空缺与过期"这条路径实际上是死代码。

**影响**：`process.md` 3.13 把「只在空白或世界已变时生成」记成已实现的设计，实际不成立。
世界推进（`strictTick` 允许开新轮）之后人设不会刷新，而人设里那句
**"你的国家正在衰落/恢复（近年人口变化 +N）"** 会与实时 `systemSection` 的数据互相矛盾——
恰好踩在 skill 最强调的"趋势是决策核心"上。
（切存档时因为传了 `force:true`，人设是刷新过的，所以多国演练暂时不会踩到；影响面：中。）

**建议**：让 `leaderAgent()` 的默认文案写进 `systemPromptAuto`，或给默认人设加一个
`systemPromptIsDefault: true` 标记，使 `autofillSystemPrompts` 能区分
"服务端默认"与"使用者手写"——这样 `stale` 分支才真正生效。

## 4. 附带收获：两套时间刻度的锚点（解 `process.md` 5.5B）

`process.md` 5.5B 说 `world.年份`（历史纪年）与事件/战争的年份（世界时间）无法换算，
并猜测存档里可能存在锚点。**锚点找到了，而且不在数据库里，是一条换算比例。**

**证据**：所有带统计库的存档，`MAX(WorldLogMessage.timestamp) / MAX(WorldYearly1.timestamp)`：

| 存档 | 历史年份 | 世界时间 max | 比值 |
|---|---|---|---|
| 1763803227 | 19 | 998 | 52.53 |
| 1763803527 | 32 | 1940 | 60.62 |
| 1763803828 | 42 | 2561 | 60.98 |
| 1763804128 | 60 | 3581 | 59.68 |
| 1763804429 | 78 | 4692 | 60.15 |
| 1786603283 | 106 | 6372 | 60.11 |
| 1786603585 | 109 | 6556 | 60.15 |
| 1786603913 | 113 | 6752 | 59.75 |
| 1786604226 | 115 | 6924 | 60.21 |
| 1786604527 | 118 | 7079 | **59.99** |

10 个存档、跨 6 个世界，比值全部聚在 **~60**：

- **世界时间 ≈ 历史年份 × 60**（即世界时间的单位约为 1/60 年）。
- 比值略大于 60（60.62 / 60.98）可用「年度表最大年份可能比当前年份小 1」解释：
  上限是 `60 + 60/最大年份`，年份 60 时正好 61.0，与实测吻合。
- 19 年那个 52.53 是**下界效应**：世界太小，年内最后一条事件发生得早。

**意义**：把事件/战争的年份除以 60，即可与 `history` 的年份对齐，
于是「**是战争先发生还是饥荒先发生**」这类跨刻度排序**可以回答**了，
agent 能真正讲清「一个国家的兴衰史」。

**置信度**：**经验规律**（10 存档、跨 6 世界、比值稳定），**未从游戏代码确认**。
**可证伪实验**：在游戏里推进 1 年，看 `WorldLogMessage` 的最大 `timestamp` 是否正好 +60。
建议确认后再写进 skill 与数据字典。

## 5. 我自己的测量纠错（4 次「假的失败信号」）

写下来是为了后人别重复——这 4 次都像 bug，实际是我的测量错：

| # | 我一开始看到的 | 真相 |
|---|---|---|
| 1 | 每国 `history` 恰好 **8 行**（可疑的整齐） | 我读的是 `h.get("history", h)`，而键名是 `series` → 量到了**顶层键个数 8**；真值 **19 行** |
| 2 | `我的城市 = 0` | 键名是 `城市列表_按无家可归排序_仅前8座`；真值 **8 座**（代码是对的） |
| 3 | 「每角色每轮注入合计 = 0.0 KB」 | 我的 `kb()` 只接受字符串，传数字就把数字长度当字节数；真值 **13.8 KB** |
| 4 | `world_connector.py` 退出码 **-1** | `Select-Object -First N` 截断管道所致；真值 **0** |

另有：`Get-Content -Raw` 把 UTF-8 中文显示成 `缁濆涓嶅瓨鍦ㄧ殑瀛樻。`，文件本身是好的（`process.md` 4.10 同款陷阱）。

**教训**：在这个项目里，「整齐得可疑的数字」和「醒目的非零退出码」都要先怀疑测量方式，再怀疑代码。
