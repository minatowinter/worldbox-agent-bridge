# 把游戏数据接给 AI agent

这份 skill 来自一个真实项目：把 WorldBox 的局面接给多个扮演国家领袖的
LLM agent。过程中我逆向出了存档格式、逐个校验了字段语义、
踩了六个"不报错但结果错"的坑。

**这里的方法论适用于任何"本体不给你 API，但会把状态写到磁盘"的程序。**

---

## 一、先判断这条路走不走得通

外置读游戏数据有三条路，优先选第一条：

| 路子 | 代价 | 何时选 |
|---|---|---|
| **读程序自己写的文件** | 低（无注入、无逆向、跨版本稳） | ✅ 首选，先查有没有 |
| **读进程内存** | 高（基址、对象布局、版本一改就废） | 只在没有任何持久化输出时 |
| **注入 / 挂插件** | 中高（等于写 mod，可能违反约束） | 用户明确同意时 |

**第一件事是找文件，不是写代码。** 去找这些位置：

```
Windows（Unity 游戏）  %USERPROFILE%\AppData\LocalLow\<公司名>\<产品名>\
Windows（一般应用）    %APPDATA%\<产品名>\   %LOCALAPPDATA%\<产品名>\
                       %USERPROFILE%\Documents\<产品名>\
Linux                  ~/.config/<产品名>/   ~/.local/share/<产品名>/
macOS                  ~/Library/Application Support/<产品名>/
```

**要留意的东西，按价值排序**：

1. **存档文件** —— 信息最全，通常含整个世界/工程的状态
2. **附带数据库**（`.db` / `.sqlite` / `.s3db`）—— 往往是**历史统计与日志**，
   价值极高，因为存档只有"当前一帧"
3. **日志** —— 事件流水，带时间戳
4. **配置 / 缓存** —— 常用于校验枚举值含义

> **最容易被忽略、也最值钱的是第 2 项。** 我在 WorldBox 里发现了
> `map_stats.s3db`（110 张表，含每国逐年 48 个指标的 `KingdomYearly1`
> 和事件流水 `WorldLogMessage`）。**没有它，agent 只能描述现状，
> 无法判断兴衰**——这是"接数据"和"截图给 AI 看"的本质差别。
> 找到存档后**一定**再看看同目录有没有数据库。

### 怎么快速判断格式

```python
raw = open(path, "rb").read(4096)
print(raw[:64].hex())
```

| 开头 | 可能是什么 |
|---|---|
| `{` 或 `[` | 明文 JSON —— 最好，直接读 |
| `PK\x03\x04` | ZIP —— 解开看里面 |
| `SQLite format 3.` | SQLite —— 用 `sqlite3` 读 |
| `x\x9c` / `x\x01` / `x\xda` | **zlib 压缩** —— 通常是同一份 JSON 压的 |
| `\x1f\x8b` | gzip |
| 其他 | 自定义二进制 / protobuf，成本高，先找有没有更简单的 |

**关键经验**：同一个游戏的**自动存档**和**手动存档**可能用不同容器。
WorldBox 的 `.wbax`（自动）是**纯 JSON**，`.wbox`（手动）是 zlib 压的同一份内容。
所以**每种扩展名都要试一遍**，不要看到二进制就放弃。

```python
def decode_payload(path):
    raw = Path(path).read_bytes()
    if raw[:1] == b"{":
        return json.loads(raw.decode("utf-8-sig"))
    for wbits in (15, -15, 47):          # zlib / raw deflate / gzip
        try:
            return json.loads(zlib.decompress(raw, wbits).decode("utf-8-sig"))
        except (zlib.error, UnicodeDecodeError):
            continue
    raise ValueError(f"无法识别: {raw[:4].hex()}")
```

## 二、字段语义必须逐个校验，不能靠字段名猜

**这是本 skill 最重要的一节。** 字段名看起来是什么意思，**不代表它真的是**。
我在 WorldBox 里连续踩了四个：

| 我以为 | 实际 |
|---|---|
| `cities[].army` 是城市驻军 | **城市记录根本没有这个字段**，读出来恒为 0 |
| `kingdoms[].buildings` 是建筑数 | 王国记录也没有；要按 `buildings[].cityID` 反查 |
| 城市有坐标 | 没有；只能拿 `zones` 所有格子算重心 |
| `width`/`height` 是地图尺寸 | 是**引擎内部分块数**（4×4），不是地图大小 |

### 校验手段（按可靠性排序）

1. **拿游戏自己的统计来对账**（最强）
   如果游戏内有任何地方展示或记录了这个数字，就和它比。
   我在 `KingdomYearly1` 里找到了军队数，本工具算出 309、它写 356——
   差异来自"统计年初记一次 vs 即时值"，**两者都对**，这反而证明字段读对了。

2. **交叉求和**
   逐城人口之和 是否等于 全国人口？逐项相加 是否等于总数？
   **不等就说明口径不一致**（我正是靠这个发现船只被算进了人口）。

3. **分布是不是合理**
   ```python
   vals = [a.get(f) for a in rows if f in a]
   print(len(vals), "字段存在率", collections.Counter(vals).most_common(8))
   ```
   - **存在率低** → 这字段可能只在特定条件下才写（我因此发现"年龄不写入存档"）
   - **取值诡异**（如 `loyalty` 出现 1171）→ 可能不是我以为的那个量

4. **看取值范围对不对**
   说好的百分比却出现 1789862958？那就是拿错了字段。

### 记录口径，并在文档里写明

每个派生指标都要写下"怎么算的 + 为什么这样算"。示例：

```
人口 = actors_data 里 civ_kingdom_id 匹配的角色数，排除船只
军队 = 上述角色中带 army 字段的数量（城市记录里没有 army）
领土 = 各城市 zones 数组长度之和
```

## 三、设计 agent 友好的信息层

数据能读出来只是开始。**直接把原始存档丢给 agent 是没用的**——
24 MB 的 JSON 既读不完，也抓不住重点。

### 3.1 五条设计原则

**① 一实体一文件，而不是一个大 JSON**

```
data/nations/<名称>/self.json      本国
data/nations/<名称>/others.json    他国视角
data/nations/<名称>/history.json   趋势
```

好处：agent 只打开自己那份，不必在巨文件里筛选；也不会误读到别的实体的内部。

**② 引用要解析成名字，不要只给 id**

`{"kingdomID": 32}` → `{"敌方": [{"id": 32, "名称": "莱国"}]}`。
agent 不需要查表就能说话。**但它仍然需要 id**（用于精确查询），所以两者都给。

**③ 键名稳定、值可读**

键用固定英文（程序可以安全依赖），值用 agent 与人能直接读的语言。
枚举另给 `label`：`{"id": "wise", "label": "睿智"}`。

**④ 体量有上限，超大集合只做汇总**

- 列 8 座最要紧的城市，而不是全部 40 座
- 不列 2000 个单位，给人口/军队/职业分布
- **但趋势序列要完整**——那是决策依据，不能截断

**⑤ 缺失就说缺失，绝不用默认值填充**

```python
# 错的：读不到就给 0，agent 会以为"忠诚度是 0"
"loyalty": city.get("loyalty", 0)

# 对的：读不到就不给这个键，或明确标注
"loyalty": None  # 并在 _note 里写「存档不记录城市忠诚度」
```

> **为什么这条最重要**：agent 的决策质量完全取决于情报真实性。
> 一个编造的 0 比一个缺失的字段有害得多——前者会让 agent 自信地做出错误决策。

### 3.2 必须注入"数据新鲜度"

**每个 agent 的上下文里都要带"这份数据是多久以前的"。**
不这样做，agent 会把几小时前的状态当实时局势，而它**完全没有能力自己发现**。

```json
"数据新鲜度": {
  "存档距今秒数": 268.5,
  "警告": "⚠️ 数据已 4.5 分钟旧，游戏可能已暂停或关闭，请勿当作实时局势"
}
```

**光在文档里写纪律是不够的，要代码主动报警。** 超阈值就在结构里加 `_警告`
字段，并在命令行工具里往 **stderr** 打印提示（不污染 stdout 的 JSON）。

### 3.3 趋势是决策的核心，不是可选项

单点的"人口 1767"什么也说明不了。**"从 2921 掉到 1716"才是信息。**

实测对照：同一份数据，看到"人口只恢复到峰值 59%"的谨慎角色选择休养；
看到"敌人只有 25 兵"的好战角色选择出击。**没有趋势，角色只能描述现状。**

所以：
- 一定要找历史数据源（第 1 节说的那个数据库）
- 注入时给出**数值序列 + 变化量 + 年份区间**，不要只给最新值
- 明确告诉 agent "看趋势，不要只看当前一帧"

### 3.4 同一个指标有两套值时，都给出

游戏常有"即时值"与"定期统计值"。**不要选一个假装另一个不存在**，
那会让 agent 觉得数据自相矛盾：

```json
"knowledge": {
  "口径歧义提示": [
    "『声望』这里是即时值 1623；history 最新一行的 renown 是 1639。
     两个都对，只是时间点不同：判断当前用即时值，判断趋势用 history。"
  ]
}
```

### 3.5 明确声明信息边界

```json
"knowledge": {
  "可以确信": ["本国全部数据", "本国完整事件记录"],
  "仅为估算": ["他国人口的数字是精确的，但内政只能看到表象"],
  "无法得知": ["他国军队的具体位置", "任何角色的年龄（存档不记录）"]
}
```

这比让 agent 自己摸索"哪些能信"有效得多。

## 四、接入多 agent 平台

如果你要把这些数据接进一个多 agent 对话平台，有四个必答题。

### 4.1 世界推进 → 驱动新一轮，而不是定时器

游戏存档是有节奏的（WorldBox 约 5 分钟）。**如果平台按自己的循环开新一轮，
agent 会在同一帧数据上反复决策、反复产出同样的结论。**

```python
fingerprint = f"{save_path}|{save_timestamp}"
if fingerprint == last_fingerprint:
    return          # 世界没变，不决策
```

**要给平台一个明确的"世界是否推进"判断。**

### 4.2 平台级上下文必须压缩

完整情报可能 27 KB。**每个 agent 每轮都灌 27 KB 既贵又没用。**
压到 3–5 KB：保留最要紧的少量明细 + 完整趋势 + 对手对比。

**要压什么、留什么，取决于"决策真正需要什么"**——这是设计问题，
不是工程问题。问自己：一个真实决策者会先看哪几个数字？

### 4.3 agent 不能直接改变世界 → 必须有动作闭环

**如果游戏只有你能改，那 agent 只能"提案"。** 这带来一个闭环要求：

```
agent 提案 → 平台收集成待办 → 人来执行 → 结果回填 → 下一轮 agent 知道生效没有
```

**没有回填，agent 几轮之后就会敷衍**——它发现说什么都没用。

设计要点：
- 提案要有**唯一 id + 状态**（`proposed`/`executed`/`rejected`/`obsolete`）
- 提案要带**世界指纹**；世界推进后，未裁决的旧提案自动作废
  （否则 agent 会看到针对旧局势的提案"没人理"）
- 提案要**可执行**：具体到"在哪个位置做什么、多少量"，而不是"发展农业"

### 4.4 让 agent 输出结构化动作，但保留原文

要求 agent 用固定格式写提案（例如 `执行：请在某地做某事`），
平台用**宽松正则**抽取成结构化条目。

**但解析失败时不要丢弃原文**——把整段留给人类看，并提示 agent 按格式重写。
**永远不要因为解析失败就丢掉 agent 说的话。**

### 4.5 多个实体 → 每个 agent 一个身份 + 一份人格

每个 agent 要能回答"我是谁"。设计上：

- 一份**国家/实体清单**（名称 ↔ id ↔ 目录），agent 用它确认身份
- 每个 agent 一份**人格档案**（设计目标/价值观/恐惧），**跨回合持久化**
- 人格可以**由数据自动生成**（实体名、领导者特质、实力地位都是现成的），
  但**绝不能覆盖使用者手写的**——存进独立字段，两者拼接使用

**跨回合记忆是关键**：没有它，每隔几轮 agent 就"失忆"，人格立不起来。
给它一个它自己能读写的记忆文件（如果平台有文件工具）。

## 五、已知的坑（都是"不报错但结果错"）

这一节值得单独背下来。**静默失败是最难查的。**

### 5.1 SQLite 跨线程

```python
sqlite3.connect(uri, uri=True)                        # 默认禁止跨线程
sqlite3.connect(uri, uri=True, check_same_thread=False)  # 加锁后可用
```

症状：主线程查询正常，工作线程**静默返回空**（异常被 `except sqlite3.Error` 吞了）。

**教训**：捕获异常时**一定要记录下来**（`self.error = ...`），
否则"没数据"和"出错了"分不清。

### 5.2 `PRAGMA table_info` + `row_factory = Row`

```python
cols = [r[0] for r in conn.execute('PRAGMA table_info("t")')]  # 错：拿到序号 0,1,2…
cols = [r[1] for r in conn.execute('PRAGMA table_info("t")')]  # 对：索引 1 才是列名
```

结果 SQL 变成 `SELECT  FROM ...`，**不报错，只返回空**。

### 5.3 只读打开，避免和运行中的程序抢文件锁

```python
sqlite3.connect(f"file:{path}?mode=ro&immutable=1", uri=True)
```

`immutable=1` 告诉 SQLite 文件不会变，跳过加锁。**读别人的活动数据时必用。**

### 5.4 原子写入（agent 可能正在读）

```python
fd, tmp = tempfile.mkstemp(dir=path.parent, prefix=".tmp-")
with os.fdopen(fd, "w", encoding="utf-8") as fh:
    fh.write(data)
os.replace(tmp, path)          # 同文件系统内原子替换
```

否则读者可能看到**半个 JSON**。

### 5.5 白名单序列化会"吞掉"新字段

症状：**"我明明写进去了，读出来却没有。"**

如果代码里有多处白名单式构造（把内部对象转成对外 DTO），
加字段时漏一处，字段就消失了。**第一反应应该是查序列化白名单，
而不是怀疑写入失败。**

（我在一个项目里同时踩了这个和上面 5.2，长得一模一样。）

### 5.6 关键词指令要在解析之前拦截

`"—save latest"` 里的 `latest` 是**指令**（恢复跟随最新），不是名字。
如果不拦截，它会被当成实体名，把选择**锁死在当前那个**上——
使用者以为恢复自动了，其实被钉住了。

**通用教训**：解析"用户给的值"时，先处理保留词（`latest`/`auto`/`none`/`*`）。

### 5.7 HTTP handler 里别用 `res` 当变量名

```js
const res = await something();          // 遮蔽了 HTTP 响应对象
sendJSON(res, 200, {...});              // → res.writeHead is not a function
```

### 5.8 给异常日志加堆栈，别只打 message

我为一个 500 排查了好几轮，因为只打了 `e.message`。
加上堆栈后**一次就定位到行号**。

### 5.9 测试不要依赖具体数据

**这条是被现实教的**：世界状态从"3 国 212 年"变成"1 国 194 年"之后，
一大批断言集体失效：

- 「事件非空」→ 新开局的世界一条事件都没有
- 「可查询他国」→ 世界只剩一个实体
- 硬编码的名称 → 实体改名了、灭亡了

**写断言时验证机制，不要验证数据：**

```python
check("事件结构正确", isinstance(events, list))          # ✅
check("必须有事件", len(events) > 0)                     # ❌
```

实体名一律**动态取**。文档示例里的每个数字都要真的算过——
**错误的示例比没有示例更糟**（我写过一个"把离敌人 26 格的部队派去打"的部署示例）。

### 5.10 临时目录的意外限制

`tempfile.mkdtemp()` 建的目录在某些沙箱下**不能再创建子目录**。
测试里需要多层目录时，用工作区内的普通目录并自己清理。

### 5.11 脚本退出时的 keep-alive

Node 里 `fetch` 的连接会让进程在退出时报
`Assertion failed: (!(handle->flags & UV_HANDLE_CLOSING))`。
给客户端加 `dispose()` 清缓存，用 `process.exitCode = ...` 而非 `process.exit()`。

## 六、开工清单

接到"把某个程序的数据接给 agent"这类任务时，按顺序做：

- [ ] **找数据**：遍历常见数据目录，列出所有文件（含存档/数据库/日志/配置）
- [ ] **判格式**：看文件头，试 JSON / ZIP / SQLite / zlib
- [ ] **看全貌**：打印顶层结构、每张表的 schema 与行数
- [ ] **逐个字段校验语义**：存在率、分布、交叉求和、与程序自带统计对账
- [ ] **找历史数据源**：有没有"随时间变化"的表/文件（这是最值钱的）
- [ ] **定义派生指标口径**，并写下"怎么算 + 为什么"
- [ ] **设计信息层**：一实体一文件、名字解析、体量上限、缺失就说缺失
- [ ] **注入新鲜度字段**，并在代码里主动报警
- [ ] **趋势要给序列**，不能只给最新值
- [ ] **写规格文档**：字段含义、口径、已知限制
- [ ] **写回归测试**：验证机制而非数据；实体名动态取
- [ ] **做接入**：世界推进驱动 / 上下文压缩 / 动作闭环 / 跨回合记忆
- [ ] **降级路径**：数据源不可用时要有明确提示，而不是让 agent 编造

---

## 七、一句话总结

**读程序写的文件，别读内存；字段语义靠对账，别靠名字；
给趋势不给单点；缺失就说缺失；世界推进才决策；agent 只能提案，
所以必须有回填闭环。**

只要这七条守住，接出来的数据就是 agent 真的能用的，
而不是"看起来很详细但会误导它"的一堆数字。
